# ADR 0012 — npm packages are first-class in the catalogue

- Status: accepted
- Date: 2026-11-04

## Context

The catalogue modelled a project's packages as NuGet packages. `packages[].id` was a
NuGet id, every version came from the NuGet flat-container index and its search entry,
the install panel offered .NET tooling, and `/releases/` listed NuGet rows. `install`
distinguished a plain package from an MSBuild SDK and a .NET tool.

Astroc4 is published to npm, not NuGet. Before this decision its catalogue record had to
declare no package at all: the project page rendered no install panel, `/releases/` never
listed it, and the browser's live version check (ADR 0008) had nothing to check. That is
not a property of astroc4 — the product family now includes a TypeScript package consumed
by a JavaScript build, and the catalogue has to say so without pretending it is NuGet.

The two registries agree on the part that matters: both return a list of published
versions and both speak SemVer, which `lib/nuget-version` already parses (it is a superset
of SemVer). They disagree on everything around it: how versions are discovered, what
"downloads" means, and how a package is installed.

## Decisions

### 1. `registry` is part of a package's identity

`packages[]` gains an optional `registry: nuget | npm`, defaulting to `nuget`. The loader
resolves the default, so every resolved package has one, and uniqueness is enforced per
`registry:id` rather than globally: the same name may exist on both registries and the two
must not be confused. The default keeps every existing record unchanged.

### 2. Versions are read from the registry that publishes them

- **NuGet** keeps the flat-container index plus the search entry (description, total
  downloads, deprecation, unlisted). Target frameworks are still read from the `.nuspec`.
- **npm** reads the registry document with `Accept: application/vnd.npm.install-v1+json`
  — the abbreviated representation, because the full document carries every version's
  manifest. The version list is the document's `versions` keys, the channel tags are
  `dist-tags`, deprecation comes from the manifest `latest` resolves to, and downloads are
  the last week's from the npm downloads API.

GitHub release tags still fill a gap the registry list has not caught up with, for both
registries, using the same floor rule as before.

### 3. The install panel follows the registry

`installTabs(registry, kind, packageId, version)` renders npm/bun/pnpm/yarn tabs for an
npm package and keeps the existing .NET tabs for NuGet. `install` remains a NuGet-only
choice: it has no meaning for a package a JavaScript package manager installs.

### 4. Live version checks cover both registries

The browser check of ADR 0008 is no longer NuGet-specific. A package is addressed by
`registry:id`, the stored payload is keyed the same way, and each registry is fetched from
its own endpoint. A build-time version is still never downgraded by a live one.

### 5. Registry-specific checks stay registry-specific

`status: stable` means a stable version on the registry that publishes the package.
NuGet-only observations (target frameworks, search deprecation, unlisted packages) apply
only to NuGet packages; npm deprecation is reported from its own document. The site labels
downloads by period — total for NuGet, weekly for npm — because the numbers are not
comparable and must not be presented as if they were.

## Consequences

- A project may declare packages from both registries; each is summarised, installed and
  linked on its own terms. The release rollup still compares versions with the SemVer-aware
  comparator, which is the one rule both registries share.
- The release cache schema moves to version 3 and carries `npmPackages`; the committed
  fixtures are regenerated by `just refresh-fixtures`, and the offline fallback keeps
  working.
- Astroc4 declares `@purview-dev/astroc4` with `registry: npm`, so it now has an install
  panel, a row on `/releases/`, a package link on its project page, and a live version
  check — with `status: preview`, because npm has published prereleases only.
- `registry` is vocabulary: adding a third registry (Maven, crates.io) is another
  ADR-level decision, not a free-text label.

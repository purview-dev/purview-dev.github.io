# ADR 0007 — Search and AI discovery

- Status: accepted
- Date: 2026-03-10

## Context

The site must be discoverable by search engines (Google, Bing, Qwant, Startpage
via its upstream indexes), by AI search crawlers (ChatGPT Search / `OAI-SearchBot`)
and by tooling that consumes `llms.txt`. It must also be able to notify IndexNow
participants after a deployment, and it must do all of this without a
hand-maintained list of URLs that can drift from the catalogue.

## Decisions

### 1. One discovery model drives everything

A single `DiscoverableResource[]` (`src/src/lib/discovery/`) is derived from the
project catalogue (`loadProjects`), the aggregated documentation manifest
(`readDocsManifest`) and the release cache. The sitemap, `robots.txt`,
`discover.json`, the per-project `llms*.txt` bundles and the IndexNow submission
all read that one model, so they cannot disagree about what exists.

### 2. The sitemap is generated by an Astro integration, not `@astrojs/sitemap`

`@astrojs/sitemap` emits a single `sitemap-0.xml` and cannot express the
partitioned structure or content-derived `lastmod` values we need. The
`purview-discovery` integration (`src/config/discovery-integration.ts`) runs at
`astro:build:done`, receives Astro's complete route list (the same mechanism the
plugin uses, so no page is missed) and writes:

- `/sitemap-index.xml` → `/sitemaps/pages.xml`, `/sitemaps/projects.xml`,
  `/sitemaps/llms.xml`;
- `/robots.txt`;
- `/discover.json`;
- `/projects/<slug>/llms.txt` and `/projects/<slug>/llms-full.txt`.

The IndexNow key verification file (`/<INDEXNOW_KEY>.txt`) is written separately
by the deploy workflow from the `INDEXNOW_KEY` secret, so the build never sees
the key.

### 3. `lastmod` is content-derived, never the build time

A sitemap whose every URL claims to have changed on every deploy teaches
crawlers to ignore the signal. Each resource is dated from the source that
produced it: the last commit that touched the source file (one bulk `git log`,
indexed in memory), the project's latest release date, or the documentation
page's own `lastReviewed` date, with the release-cache retrieval time as a coarse
fallback. The deploy workflow checks out full history (`fetch-depth: 0`) so the
per-file dates are real.

### 4. Per-project machine-readable content uses the llms.txt convention

The emerging `llms.txt` convention is applied at the per-project scope:
`/projects/<slug>/llms.txt` (a concise index) and `/projects/<slug>/llms-full.txt`
(the full documentation corpus). This replaces the previous, non-standard
`/_llms-txt/<id>.txt` paths. `llms.txt` is treated as a convention, not a
search-engine protocol; the canonical HTML pages remain the primary content.

### 5. IndexNow notifies changed URLs only, after a successful deployment

`discovery:indexnow` compares the previous deployment's public `discover.json`
(captured before the deploy and re-published as `/_discovery/previous.json`) with
the new one, and submits only added/modified URLs to the protocol-wide endpoint
`https://api.indexnow.org/indexnow`. It supports `--dry-run` (no network, no key)
and never logs the key. It runs in a separate job that `needs: deploy`, so a
failed deployment never announces new URLs, and an IndexNow outage never rolls
back a successful deployment.

### 6. `discover.json` is Purview-specific

`discover.json` is our own versioned discovery API, clearly documented as
non-standard. Internal deployment state (with per-URL hashes) is kept out of the
published output.

## Consequences

- Adding or removing a project changes the sitemap, `discover.json`, the LLM
  bundles and the IndexNow diff automatically; there is no URL list to maintain.
- `just validate` / `bun run ci:build` fail on discovery drift via
  `discovery:validate`.
- One-time operator steps remain: register the domain in Google Search Console
  and Bing Webmaster Tools, and set the `INDEXNOW_KEY` secret. See
  `docs/discovery.md`.
